## 1. 保存内容与边界

- `SessionSave`整体包含会话状态（当前局、金币、下一局序号、下一命令序号）、完整结算奖励账本，以及教程／种子／起手选择。未实现的广告、购买、成长、音效设置没有伪造状态或按钮。
- 当前局含背包实例／放置／备存／撤销历史、波次与阶段、生命、战斗RNG／冷却／攻击与耗材计数、掉落选项、战报统计、结算状态与已处理命令ID。战报面板此前累计的全部显示条目并未作为历史日志单独持久化；恢复后可重建最近保存批次。
- 所有正常命令和波次边界先确认存档，再发布给界面。战斗中最多间隔10个模拟tick（1秒）建立检查点，前后台切换尽力立即保存；**异常终止可能回退到最近已验证检查点，不承诺保存最后一个tick**。
- 战斗恢复先暂停，须点击“继续战斗”；不补算后台时间。教程已读标记保留，但未完成教程的中间页码不保存。
- 只针对同一本机预览入口验证；浏览器存储随站点来源和浏览器环境区分。请使用稳定入口`http://127.0.0.1:4173`；改成localhost、其他端口／浏览器、清除站点数据或无痕窗口，不应期待读取同一份档。没有账号或跨设备云同步。
- 组合根注入Cocos本地键值存储，纯核心不依赖cc、DOM、真实时钟或平台SDK。**TapTap原生真机存储、配额、断电／杀进程及前后台生命周期仍未验证。**

## 2. 完整信封与中断恢复

信封采用`schemaVersion=1`，记录revision、contentVersion、RNG算法版本、安装身份、完整payload、extensions和checksum。规范JSON按键排序，非ASCII字符串转为UTF-16转义，数值限安全整数；`crc32-ascii-json-v1`只检测意外损坏，**不是加密、签名或防作弊**。参考向量含空串CRC32=00000000、123456789=cbf43926，以及中文／emoji序列化。

三个逻辑槽均存完整信封：`bureau.preview.v1.current`、`bureau.preview.v1.backup`、`bureau.preview.v1.pending`。

提交顺序：校验payload与baseRevision → 重读各槽排查已有冲突 → 已验证旧档写备份并读回（若备份已是该已验证旧档，则保留、不重写唯一有效备份） → 新候选写pending并读回 → 同一候选写current并读回 → 发布已确认状态 → 尽力清候选。清候选失败不否定已读回的主档提交。

恢复时先检查所有槽是否出现未来schema，再校验checksum、内容版本和业务不变量；选择修订号最高的完整有效信封。候选恢复直接载入钱包与回执，**不重执行金币加法**。相同revision不同内容、安装身份冲突、未来schema、不匹配内容／未知装备均停止写入，保留原始数据；全部坏档不会静默清零。当前故障界面只提供不破坏数据的“重新读取存档”，**尚无界面导出、确认重建或旧schema迁移功能**。

协议是单进程串行与读回校验，不是数据库ACID；多页面预读可识别普通旧快照，但没有原子跨进程CAS，也不承诺所有平台的物理持久性。奖励账本不自动截断。

## 3. 初始武器入口修复

`availableStarters(content)`按当前内容中已解锁的weapon定义生成列表；菜单、开局和存档校验共用规则，不再写死三个ID。四武器使用2×2卡片布局，超过四把可分页，不通过窄卡片无限压缩。
