## 2. 纯核心契约

核心函数形态为“当前状态 + 命令 + 配置 + 显式 RNG 状态 → 新状态 + 领域事件／结果”。失败返回带原因的结果，不半改状态后再抛异常；不可变快照可用于回滚与重放。

**禁止核心引用 cc、tap、DOM、window、document、localStorage、Math.random、Date.now 或真实定时器。**核心不读取设备、网络、文件、广告 SDK、音频或渲染节点。项目静态检查应验证导入边界与禁止调用；字符串搜索只能辅助，不能代替 AST／依赖检查。

核心对象：

- InventoryState：实例表、格子派生索引、备存区顺序、revision；占用索引与组合可重建，不保存互相矛盾的双份真相。
- RunState：runId、mode、contentVersion、dateKey（可选）、五波进度、phase、布局、当前战利品、复活额度、整局重抽已使用标记、随机事件与各随机流状态。
- CombatState：tick、deadlineTick、角色／敌人状态、冷却、消耗品次数、组合计数、RNG、单调事件序号与统计。
- ProfileState：金币、升级、解锁、图鉴、成就、每日记录、已结束局摘要、下一个局序号；不得从 UI 文本推算真实余额。
- RewardLedger：稳定业务奖励键与已提交回执；奖励类型、数量、来源、应用 revision 都可审计。

所有 ID／整数／枚举／数值边界在入口校验。金币采用非负安全整数；NaN、Infinity、非法权重、未知配置引用、零冷却、重复实例、超范围朝向均拒绝。配置错误显示可定位诊断，不默默替换随机内容。

## 3. GameServices 与端口注入

GameServices 是**每次应用启动创建的一组实例**，在 Cocos 组合根集中装配后显式传入用例／控制器；不挂到全局变量，不让战斗通过单例查找广告。测试直接注入内存／假时钟／可控广告等真正实现。

| 端口 | 拟定职责与约束 |
|---|---|
| Storage | 读写完整信封文本、读回校验、报告配额／不可用／写入失败；能力与原子性须由适配器明确说明，不承诺底层必然原子写 |
| Clock | 分开提供 UTC 墙钟和单调前台计时；日期只由应用层换算 UTC+8，战斗仅接收显式 tick；每日挑战本地日期不自动重置广告日预算，后者按广告设计单独核验 |
| Rng | 从指定根种子与命名空间创建可快照的随机流；含算法版本；测试可注入固定序列，不使用全局随机 |
| AdService | 自愿激励请求、可用性、生命周期和结构化结果；不决定金币数、不直接改游戏存档 |
| Login | 区分游客、取得一次性 code、经可信服务端确认的身份；MVP 不创建服务端，是否必须兑换及上线许可须官方确认；取得 code 不是登录认证完成 |
| Audio | 根据表现事件播放／停止，遵守用户设置和生命周期；音频失败不得改变战斗结果 |
| Lifecycle | 前台／后台／中断订阅与释放；应用层管理暂停原因集合、快照和恢复，不在适配器内偷偷推进战斗 |
| DesktopShortcut（追加平台端口） | 官方指引把“添加到桌面”列为必接能力；提供真实入口与结果反馈，已核对 tap.hasHomeScreenWidgetAndPinned / tap.createHomeScreenWidget；开发包无法完整测试，按线上受控版本补验，不用网页收藏或空按钮冒充 |

接口中的名称均为项目设计，不是猜测 SDK 名称。缺少平台能力时返回明确的 unavailable／unsupported，不以空实现伪造成功。阶段 2 可用标明“仅本次会话”的内存 Storage；阶段 3 才承诺经过测试的本地持久化。

预览环境可以使用浏览器或内存适配器；正式包只选择已核实的 TapTap 原生适配器。构建配置必须区分 preview／mock／taptap-production，不靠检测某个全局变量后随意降级成“正式可用”。

## 4. 状态机与命令提交

主状态：Boot → Menu → Preparation → Combat → Loot → Preparation；第 5 波胜利进入 Settlement；任意战斗失败进入 DefeatPending，可复活回 Combat 或结束进入 Settlement；Settlement 完成后回 Menu。

- 每个命令带 commandId、runId、预期 phase／revision；应用命令串行，拒绝旧界面、双击、异步迟到回调对新局操作。
- 背包检查点只属于当前 Preparation；StartCombat 先验证实例集合、计算组合并封存布局，成功后关闭撤销窗口。
- 波次胜利键、战利品领取键和本局终局键均稳定；重复处理同一事件返回已处理回执，不生成新物品、不重复金币。
- DefeatPending 保存可恢复快照；点击直接结算会永久关闭该局的复活资格。已结束局不能因为迟到广告恢复成 Combat。
- 动画订阅已提交事件，可跳过／重播；动画结束、音频结束、按钮文字改变都不是提交条件。
- 广告是应用层的一个待完成机会，不把“加载中”写进敌人 AI。请求进行时保留不看广告的正常路径；取消后的归属和迟到结果按广告协调规则处理。项目取消／超时不代表能主动关闭原生覆盖层，归属未知时可暂停后续真广告而不是阻断基本游戏。

开发时对状态跃迁建立显式允许表。任何不允许的命令只返回原因与诊断，不做部分变更。

## 5. 确定性随机、战斗调度与暂停

- 根种子、contentVersion、RNG 算法版本和流命名规则一并记录；基于稳定字符串／整数规范派生，不依赖对象哈希或平台字符串遍历差异。
- 流按用途与机会隔离，例如 combat/wave-2、loot/wave-2/base、loot/wave-2/reroll-1、event/wave-2、cosmetic。示例是命名空间，不是文件路径。
- 内容配置载入后排序与校验；事件序号、敌人／装备 spawnIndex 决定同 tick 的处理顺序；事件中的墙钟日志时间不能参与重放哈希。
- 应用层以固定 100ms 步长请求推进；渲染只读取快照并插值。一次推进多个 tick 必须等价于逐 tick 推进。
- 为每帧设置有限追赶次数；积压过大时放慢模拟并记录性能诊断，不跳过战斗事件。进入后台／广告／系统中断时冻结并清空墙钟积压；恢复不追补后台时间。
- 暂停原因使用集合，如 background、ad、user、system；只有前台且所有原因解除、用户完成恢复确认后才能推进。一个 onShow 或一次广告结束不能覆盖其他暂停原因。
- 广告和普通音效／特效使用独立状态，不消费游戏 RNG。旋转拖动预览也不能消费战斗 RNG。

后台保存尽力完成最近快照，但不假设平台给足异步时间。每次备战封存、波次结束、领取、购买、结算及奖励提交都建立持久化点。异常退出回到最近**已验证**的快照，不能宣称总能恢复最后一个 tick。

## 6. 本地存档：全状态单信封

### 6.1 信封内容

拟从 schemaVersion=1 开始，字段含 schemaVersion、revision、contentVersion、checksumAlgorithm、checksum、profile、run、rewardLedger、adPolicyState、pendingOpportunities（含尝试、可信证据和原机会上下文）、settings、tutorial、firstExperience。checksum 对除自身之外的规范化内容计算；算法和参考向量在阶段 3 前锁定。

信封包含全部需保持一致的业务状态；禁止把金币、奖励账本、复活状态分散为互不关联的独立键。写入广告增量须读取最新信封，不用旧快照覆盖新背包／新局；同 schema 下允许保留的扩展字段不能被某个模块随意丢弃。checksum 是损坏检测，不是加密、签名或防作弊证明。

存储槽：current、lastValidBackup、pendingCandidate，**每个槽都是完整信封副本**；这些是逻辑键，不是擅自确定的平台文件路径。备份不能被未经校验或未来版本数据覆盖。

### 6.2 可恢复提交协议（待故障注入验证）

1. 单写队列中检查 baseRevision，纯 reducer 计算完整 nextState 与 revision+1，并执行不变量检查。
2. 将已验证的当前信封保存为 lastValidBackup 并读回确认；若只有备份有效，先保留该备份，不能拿坏主档覆盖它。
3. 把 nextState 写入 pendingCandidate 并读回检查版本、checksum 与内容约束。只有完整有效候选可作为恢复来源。
4. 将同一信封写入 current 并读回确认，才向 UI 确认“已保存／已发奖”；候选清理失败不影响已确认结果。
5. 重启后校验各槽，在没有未来版本阻断的前提下选择 revision 最高的完整有效信封；相同 revision 内容不同视为冲突，停止写入并保留证据。有效 pendingCandidate 可以完成恢复提交，但**不能再执行一遍金币加法**。
6. 成功恢复后显示“已从备份／中断提交恢复”；保留最后一个有效旧版本。底层写入任一点失败时，旧／新全状态二者至少按实际适配器能力恢复其一，不能混合出“有金币、无账本”。该目标必须通过模拟和真机断点测试，当前未验证。

这不是数据库 ACID 保证：依赖平台存储的实际持久性、配额和进程终止行为。单写队列只约束本进程；不承诺两个进程同时改同一存档的 CAS 安全。检测到冲突进入只读／恢复界面，不自动“合并余额”。

### 6.3 损坏、迁移与未来版本

- 主档坏、备份好：只使用验证通过的备份／候选恢复，明确告知可能回退最近进度。
- 全部损坏：保留原始内容，提供导出诊断与经用户确认的新建存档；不得静默重置为零金币。
- 旧 schema：依次运行纯迁移 vN→vN+1，在内存验证完整结果，保留迁移前信封后再走可恢复提交；失败不覆盖源数据。重复启动不能重复支付迁移奖励。
- **任一槽能够解析出高于程序支持版本的 schemaVersion，默认停止自动写入并保留原始信封，提示升级；即使其 checksum 算法尚不认识，也不能把它当作坏档用旧备份覆盖。**
- 内容变更与存档 schema 分开：未知装备实例进入保留／隔离视图，不删除；不兼容旧局不能强行用新伤害配置继续。提供明确的内容迁移或暂停该局，保留可迁移的局外数据与原始快照。
- runId 使用持久化局序号与安装级随机命名空间形成，不能只用秒级时间；下一局序号在建立新局时同次保存，恢复不重复创建已发奖局。

首版奖励账本不因达到存储预算而自动删除。后续若需归档，必须证明所有仍可能重放的奖励键仍可去重，并单独升级 schema 与增加测试。

## 7. 广告奖励与存档的一致性

此处只规定领域边界；SDK 回调、完播证据、超时与单例细节见配套广告设计。正式广告单元 ID 只从外部配置读取，缺失就禁用该能力，不能臆造 ID 或把模拟成功当正式播放。

attemptId 标识一次播放尝试；rewardKey 标识一个业务资格，重试不能换奖励键。例如：

| 奖励／提交 | 稳定业务键示例 | 同信封需要改变的内容 |
|---|---|---|
| 普通局基础结算 | runId + settlement | 终局状态、固定基础金币、钱包、结算回执 |
| 复活 | runId + revive | 复活次数、战斗恢复状态、对应奖励回执 |
| 战利品重抽 | runId + loot-reroll | 整局重抽已使用、原 waveId／opportunityId、新方案与 RNG 状态、奖励回执；不按波创建新额度 |
| 金币翻倍 | runId + settlementId + base-bonus | 只补发该局已确定的基础金币、钱包、奖励回执 |
| 成就 | achievementId | 领取状态、钱包、奖励回执 |
| 每日首胜 | daily + dateKey | 当日领取状态、钱包、奖励回执；不因 contentVersion 改变重复领取 |

流程：先检查资格与用户主动选择 → 展示前持久化同业务机会、原上下文和策略预算预留 → AdService 返回结果 → 验证有效的完整观看证据写入全存档 → 去重检查 → 同次可恢复提交奖励回执与实际游戏收益 → UI 播放动画。展示前持久化失败不调用正式展示；普通流程照常。

- AdService 只返回结构化结果，例如 completed、incomplete、unavailable、load_failed、show_failed、cancelled、timeout；这是项目枚举，映射规则不能杜撰 SDK 承诺。
- 同一请求重复回调、不同尝试重复回调、结算按钮连点，都通过同一个奖励 reducer／提交队列去重。重复调用返回原回执，不重新给金币或复活。
- 只记录 attemptId 不能证明 SDK 的迟到事件属于新请求；实例代次、绑定窗口与证据不足时的处理交给广告适配与契约测试，不做虚假的“必然正确关联”保证。
- 存档失败或回执不明时先重读 revision／账本核对是否已提交，不盲目回滚或重发；不提前播“领取成功”，保留内存中待提交奖励以便核对后重试保存；不要求用户为同一已记录完成结果再看广告。普通流程仍可取消广告并继续；若整体存储不可用，明确提示临时会话／未保存状态。
- 重启可恢复已经完整保存的待奖励记录或完整奖励信封；不把“曾开始播放”推断为“已完整观看”。
- **无法保证的窗口：SDK 报完播后、任何本地证据持久化前进程立即死亡。没有服务端时无法完美恢复该奖励；证据未知时不自动发奖，可在原资格仍有效时再次主动尝试，并如实说明可能重看。**
- 本地 checksum 与账本不能防篡改，不能保证跨卸载、跨设备、备份回滚后的全局去重。MVP 不宣称具备服务器级经济安全。

首个正常局整局与每日挑战禁广告；后续同时满足平台与产品策略。不得自动弹出激励视频、因广告失败卡住基本流程、把展示成功当完播、把结算动画当发奖事务。

## 8. 配置、日志、安全与隐私

配置至少分三类：版本化游戏内容、环境能力开关、平台标识／广告位配置。游戏内容可以入库；私密密钥不进入客户端，广告位等公开标识也不写死在战斗逻辑。生产构建检查 mock 开关、缺失配置、许可与平台适配状态；未核实接口不填“类似平台”的替代实现。

日志为结构化记录，含 sessionId、runId、contentVersion、schemaVersion、revision、逻辑 tick、事件序号、模块、错误码、耗时、种子及经裁剪状态摘要；应用层可补观测时间，但不参与确定性计算。保存启动、异常、存档恢复与测试输出，开发者可按种子重放。

- 不记录登录 token、授权码、账号原始标识、设备广告标识、Cookie 或完整 SDK 原始对象；错误信息做脱敏再写盘。
- MVP 不建设在线分析／账号服务；留存与玩法事件默认本地记录、用户／测试者主动导出。正式 SDK 可能涉及的个人信息处理须按实际接入核查，不写“绝不联网”的错误声明。
- 据已核查的官方资料，tap.login 只返回一次性 code；完整 openid 登录文档要求由服务端执行 code2Session。secret、session_key 不得放客户端，code 不作为用户 ID、认证凭据或成功登录标志，不写日志。
- MVP 保持无服务器；“上架是否必须完成服务端兑换，是否允许游客／仅取 code 的离线模式”是上线前官方工单确认项。未澄清不擅自加后端，不宣称完成真实认证。登录失败、取消和未配置不阻断开发期离线核心玩法，但不等于已满足平台上线要求。
- 添加到桌面属于已核实的必接能力；准确 API 与 iOS 差异见平台核查。阶段 5 完成接口接入和可执行契约检查；官方明确开发包无法完整测试，因此真实线上结果单列待受控版本补验，补验前不宣称全量发布就绪，不能用模拟成功消除此门禁。
- 测试日志与商业发布包隔离，导出时清除机器用户名、路径中的个人信息和敏感字段。诊断日志采用轮转和容量上限；不能清理奖励账本来腾日志空间。
- 设置页提供声音／减少动画、教程重看、隐私说明和明确的本地清除数据确认。清除会失去进度及本地去重能力，不能暗示可云端恢复。

## 9. 原生上线风险门禁

以下为官方核查结果摘要，来源、页面和后续结论统一维护在 D:/taptap/Wasteland Equipment Bureau/docs/phase-1/02-platform-verification.md：

1. 添加到桌面为必接能力，但具体 API 尚待核对；未核实／未真机验证不能标记完成。
2. 一次性登录 code 不等于 openid 认证；服务端兑换是否为本项目上架必需必须取得官方确认。无服务器方案不自行存放 secret／session_key，也不偷偷扩展为服务端项目。
3. 包体文档存在冲突：创建页写“首包 60M+”，启动优化页写“首包 4M+、总包 60M”。不能据此宣称统一 60MB 上限已核实。暂用主包 ≤4MB、完整 MVP ≤15MB 作为项目保守目标；压缩／解压、MB 计量及后台校验口径待确认，并分别实测。
4. 引擎 ZIP 与 Node 安装中只是工具准备，不代表游戏工程、适配插件、正式 SDK、真实广告或可提交包已就绪。

这些风险不妨碍纯逻辑设计，但会阻断阶段 5 原生验收和阶段 6 发布。

## 10. 实现顺序与边界验收

先按纯逻辑实现不变量与配置校验，再接 Cocos UI；先内存／模拟端口，再接通过核查的正式适配器。测试工具沿用编辑器兼容的 TypeScript 编译链，核心可编译后由已确认的本机测试运行时执行；具体命令在工具可用且脚本真实存在后登记，不伪写执行记录。

必须验证：核心无引擎／平台引用、状态机拒绝过期命令、不同渲染节奏相同事件哈希、所有存档中断点可恢复、未来版本不可覆盖、奖励与钱包一致、广告异常不阻断普通流程、前后台不补算战斗。

本文件没有创建 Cocos 工程、安装依赖或实现接口；对应自动和手动验收全部仍为 **NOT_RUN**。
